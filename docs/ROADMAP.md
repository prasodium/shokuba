# Roadmap

Shokuba is built in small, tested increments. Each phase ends with something that runs and can be inspected. Boxes are ticked only when the thing works.

## Phase 0 — Foundation

- [x] Electron + React + TypeScript (strict) scaffold, ESLint, Prettier, Vitest
- [x] Cross-platform layer (`src/main/platform`) with tests for macOS, Windows and Linux branches
- [x] SQLite with checksummed, transactional migrations
- [x] Append-only event log, typed event bus, persist-then-broadcast event store
- [x] Secret redaction on everything persisted or logged
- [x] Sandboxed renderer, validated IPC with sender checks, strict CSP
- [x] Smoke test inside real Electron (SQLite, restart persistence, real PTY, Git)
- [x] CI on macOS, Linux and Windows (typecheck, lint, unit tests, in-Electron smoke test)

## Phase 1 — First real agent + first glimpse of the office

- [x] Provider adapter interface (`ProviderAdapter` + `ObservationChannel`; the runtime owns the PTY)
- [x] **Claude Code** adapter: detect (PATH, common dirs, editor-bundled binaries) and launch in a PTY — verified against Claude Code 2.1.276, whose real interface renders in the terminal panel
- [ ] Claude Code **observed through hooks, end to end.** Hook delivery is verified against the real Claude Code 2.1.276 in headless mode (`claude -p`): the events arrive authenticated and parse. A full _interactive_ turn is **not yet verified**, because the CLI's one-time first-run setup has not been completed on the development machine. Once it has: `SHOKUBA_LIVE_CLAUDE=1 npm test -- live-claude`
- [x] Terminal panel (xterm.js): type, interrupt, resize, reconnect — verified with real keystrokes
- [x] Employee model, persisted; create / edit / remove
- [x] Minimal isometric office: an employee whose status bubble follows the event stream — verified with the demo agent, whose activity is labelled `simulated`
- [x] Demo (simulated) provider, so the office and terminal can be used and tested without an AI account

## Phase 2 — Multi-agent

Built in slices, each checked before the next.

- [x] **2a: Missions and the task graph.** Missions with tasks that depend on each other (cycles are refused); assign tasks to employees; while a mission is Running, a ready task is handed to its assignee once that agent has _reported_ itself idle; agents report back through Shokuba's own MCP tools; `submitted` is a claim, and only a person accepting it makes a task `done`. Verified with the demo agent on macOS, Linux and Windows. **Not yet verified:** a real, interactive Claude Code receiving a pasted briefing and calling the tools (the MCP handshake itself is verified against Claude Code 2.1.276 in headless mode)
- [x] **2b: Messages between agents, routing and loop protection.** Agents (and you) send persisted, structured messages; a message reaches an agent as a continuation when its turn ends, or is pasted if it is already idle; Shokuba counts the chain of replies itself and, at 6 hops, holds the message and halts the conversation for you to resume or close. Verified with demo agents on macOS, Linux and Windows, including a runaway exchange being stopped. Continuation is verified against Claude Code 2.1.276 in headless mode; **not yet verified** with an interactive session
- [x] **2c: Circuit breaker.** Watches each agent for repeated identical calls, repeated failures, failed turns, too many files edited, a turn that will not end and conversations halted as loops. It warns, then limits (no new tasks or teammate messages; the looping call is refused), then pauses (interrupted; only handing work back is allowed); stopping is only ever a person's decision. Verified with demo agents on real terminals, including a stubborn agent being paused and interrupted. A refused call is verified against Claude Code 2.1.276 in headless mode; **not yet verified** with an interactive session. **Not built:** a spend limit, because Claude Code's hooks report no cost
- [x] **2d: Teams, roles as templates, and the manager rule.** An employee is either a **manager**, who talks to you, or reports to one. **Employees who report to a manager never message you directly:** they ask their manager, who takes to you only what needs you. Shokuba enforces this itself rather than trusting the agent's instructions; an employee with no manager can still message you, and you can still write to anyone. A blocked employee's manager is told. New employees can start from a built-in role template (Manager, Engineer, Reviewer, QA) and every field, including what the role is for, stays editable. Verified with fake terminals end to end, and the rule is unit-tested at the service, the tool and the breaker. **Not built:** saving your own templates, and a manager doing anything more than being the route to you (that is 2e)
- [x] **2e: A manager drafts missions for their team.** A manager's agent is offered five extra tools (`draft_mission`, `add_task`, `remove_task`, `get_draft`, `team_status`); nobody else is. It can only draft: it may change just the missions it drafted itself, only until you run them, and assign work only to itself or people who report to it, up to 3 open drafts of 25 tasks each. You still press **Run mission**, and only you accept work. A draft says who wrote it. Verified with demo agents over real MCP connections and terminals. **Not verified:** a real Claude Code manager drafting a plan in an interactive session
- [x] Several employees running at once, each with their own terminal and desk

## Phase 3 — Git (complete)

Built in slices, each checked before the next.

- [x] **3a: The Git layer.** Making a mission branch and a branch plus working folder per task (in Shokuba's data folder, never in your project), committing a task's work as the employee, listing and showing what a task changed, and merging a task into its mission branch **without checking anything out**, with a conflict reported by file and nothing changed. It can only create or move `shokuba/…` branches, so it cannot move `main`, and a repository's hooks, filters and merge drivers never run from it. Verified against real Git on macOS, Linux and Windows. **Not yet used by tasks:** nothing in the app calls it until 3b
- [x] **3b: A branch and working folder per task.** When a task is handed out, its assignee's agent is restarted in a working folder of its own, on a branch cut from the mission's branch, so a dependent task starts from the work accepted before it. The work is saved as a commit when the agent submits (before the task shows as submitted), the task's detail shows the changed files and a diff, **accepting merges the task into the mission branch, and a conflict sends the task back to its agent** with the files named and how to fix it. A task whose folder is not a Git repository (or with Git missing or too old) runs as before and says why it was not isolated. Your own checkout and branches are never touched, and nothing is pushed. Verified with demo agents on real terminals, and with real Git in tests. _(The accept-merge and conflict path was planned for 3c; it moved here because a dependent task cannot start from accepted work without it.)_
- [x] **3c: Cleanup and the finish.** A finished task's working folder is removed as soon as no running agent is in it (when its agent moves on to its next task or is stopped, and at startup), and its branch stays, so the work can still be read. A cancelled task's unsaved edits are saved to its branch first, and a folder whose work cannot be saved is never removed. Each mission shows the branch its accepted work is collecting on, with commands to read and merge it yourself (Shokuba never merges into your branches). Verified with demo agents on real terminals, including the folder being removed after a real agent process has left it. **Not done:** task branches are kept, so a busy repository collects `shokuba/…` branches (list them with `git branch --list 'shokuba/*'`); an idle agent stays in its last task's folder until its next task

## Phase 4 — Verification (complete)

Built in slices, each checked before the next.

- [x] **4a: Checks.** Commands **you** define per project in Shokuba (never read from the task's branch, so an agent cannot add or weaken one) are run by Shokuba on the work an agent submits, in the task's own folder, on the exact commit it submitted. Setup steps (such as installing dependencies) run first; each step's exit code, duration and redacted output are kept, and a failing check does not stop the others. Nothing runs until you have acknowledged that these run agent-written code, **unsandboxed**, with your account's access. They run automatically when an agent submits (and again on request), one run at a time, and a run is dropped if the task is sent back. Accepting work whose checks failed warns you first (it never blocks you). Verified with real commands on real terminals. **Not built:** checks on a mission's merged branch, and any sandbox
- [x] **4b: An independent reviewer.** You (or, if you set it up for a project, Shokuba on every submission) ask a **different** employee to review a task's work; the author can never review their own. The reviewer is restarted in a folder of its own holding the code exactly as submitted, held to **plan mode**, and is handed what was asked and the diff, **never the author's own summary or the check results**. They hand in a verdict (approve, request changes, comment) and findings through a tool only they are offered, and it is **advice**: it never accepts, rejects or sends back anything, and accepting work a reviewer asked changes for only warns you. A review is tied to the commit it read, says when the work has changed since, and is dropped if the task is sent back. Verified with two demo agents on real terminals and real Git. **Not built:** a reviewer that runs the code or the checks, and the reviewer's own words being shown anywhere but the task
- [x] **4c: An evidence pack per task.** On any task that has been handed out, **Export the evidence pack** saves a new folder where you choose (in a dialog the app shows, so the page never names a path) holding `report.md` (what was asked, the agent's own account labelled as a claim, the commits and files, every run of the checks, every review, who accepted it and when, and a timeline from the event log), `evidence.json` (the same as data), `changes.diff` (the code exactly as Git produced it) and one log per check step. It says whether the checks and the review were of the commit the work ended at, never overwrites or follows a link, holds no full paths of its own (only the project's folder name), and records the export in the audit log. Text is redacted of secret-looking values, and the diff, which must stay exact, is scanned and the pack warns you what it found. Everything an agent or person wrote is shown as inert text, so a report cannot be turned into links, images or HTML. Verified with real Git and a real database in tests (each guarantee checked by mutation) and by exporting the pack of an accepted, reviewed task in the in-Electron smoke check. **Not built:** signing, so a pack is a record and not tamper-proof; exporting a whole mission; a zip file (a folder is easy to inspect and to archive yourself)

## Phase 5 — The office

Built in slices, each checked before the next. The rule throughout: the office reads recorded events and never invents activity. The only exception is the simulated office life of Phase 6, which is always labelled as simulation. Otherwise every movement is a picture of something that really happened, labelled `inferred` where it is deduced.

- [x] **5a: The world and the camera.** The floor plan is data (`src/renderer/office/map.ts`). _(Its layout was redesigned in 5d; what follows about the camera and the shared places still holds.)_ The shared places each stand for something real: **your inbox**, a **QA bench**, a **reading room** and the **mission board**. They stand idle for now; the board is bare, the bench screens dark and the trays empty, so an idle office never looks busy. Walls between rooms are low, with doors, and everything on the floor is drawn in depth order. The camera pans by drag or arrow keys, zooms by wheel or +/−, fits with 0, and **follows** the selected employee (bringing the view in to them); controls are real buttons, and the office is keyboard-reachable. Bubbles and names shrink with the view so a small panel does not pile them on top of each other. Verified by unit tests of the plan (nothing overlaps, every door and standing spot is clear, the plan is deterministic and rooms already there never move as it grows) and the camera maths, and by looking at the running app with 1, 5 and 9 employees, zoomed, dragged and following. **Not built:** anything moving (5b), and the places showing real work (5c)
- [x] **5d: An office that looks like an office.** The floor is now **one rectangle**, laid out like a real office and the same for every team size: along the back wall a **pantry** (tea and coffee counter, snack shelf, a high table with stools), a **glass-walled manager cabin**, **your own cabin** (the inbox) and the **lab** (QA bench, mission board); below them the **open desk area** with twelve desks, all furnished whether or not anyone sits there; and to its right a glass **meeting room** and the **reading room**. A manager sits in the cabin and their team together in the open area, in blocks of two by two. Glass walls are tall and see-through. The office panel gets more of the window. The pantry and the meeting room stand idle for now: they are where the office life of Phase 6 will happen. Verified by unit tests of the plan (the rooms tile the floor, nothing overlaps, every door is clear, every place and seat is on one connected floor, seating is right), each guarantee checked by mutation (which also caught a real bug: the pathfinder could clip the corner of a blocked cell, now fixed with an exact line-of-sight walk), and by looking at the running app, zoomed and walking. **Not built:** anyone using the pantry, the meeting room or a second manager cabin
- [x] **5b: Movement.** Employees walk. When an agent has been **running tests** for a few seconds (deduced from a command that looks like a test run), their person stands up, walks to the **QA bench** and stands there, and walks back to sit down a moment after the tests end. It is a picture of what the agent is doing, and it says so: the bubble reads _at the QA bench_ and is marked **inferred** (or _demo_), whatever the state's own label was. Calm rather than twitchy: a state must last three seconds before anyone goes, someone who has left it lingers two and a half before coming back, so a state that comes and goes never sends anyone to and fro; the bench has three spots and anyone who does not fit stays at their desk until one is free, longest-waiting first; and with the operating system's **reduced motion** setting nobody walks at all (the bubble then shows the real command instead). Paths are found by A\* on half-tile cells that keep a walker's width clear of every desk, wall and plant, never cutting a corner, and people step out of their seat to the side and back in. Follow tracks a walker. Reloading puts everyone where they belong, without walking. Verified by unit tests of the navigation (every seat, place and door on one connected floor for every team size), the walker on a fake clock, and the director, each guarantee checked by mutation (which found gaps in the tests, fixed), and by watching demo agents walk to the bench and back in the running app, with reduced motion, and with Follow. **Not built:** any other reason to walk (5c adds the handoffs of work), and the bench itself showing Shokuba's own checks
- [x] **5c: Handoffs.** Work changing hands is drawn, each one a picture of a recorded event and nothing else. A **task handed to an agent** sends a card from the mission board to their desk, and a **paper** lies on that desk while they hold it. **Submitted work** sends a card to **your inbox**, whose tray stacks one card per task waiting for you and whose tag counts them (_Your inbox · 2 waiting_); a card is marked green, amber or red by the worst thing said about it (a failed check, a review asking for changes). **Checks** light the **QA bench's screens**: amber while Shokuba runs them, green or red after (_QA bench · checks passed_), no person involved, so Shokuba's own checks never look like an agent running tests. An **independent review** in progress sends the **reviewer to a reading desk, where they sit** (their agent really is working in a separate folder), and when they hand it in a card carrying their verdict flies from them to your inbox and they walk back. A **message** between two people carries an envelope from one to the other (you are your inbox). **Accepted** work flies to the board, where it stays as a green card; **sent back** flies to the assignee, red. The board holds a card for each task waiting, blocked or lately accepted, and its tag counts them. Only news flies: opening the office never replays history; a burst of events shows the latest few, and a flight that had to wait more than six seconds is dropped as a picture of the past; with the operating system's **reduced motion** setting nothing flies and nobody walks, and the places still show where the work is. Nothing here adds a table, an event or an IPC call: it reads the missions and events the app already has, and each task's checks and review through the calls the task view already uses. Verified by unit tests of the mapping from events to flights, the flight queue on a fake clock, the derivation of what each place shows, the director's new _errands_ and the way out of a reading chair, each guarantee checked by mutation (which found one gap, fixed, and one dead value, removed), and by running the whole story with the demo agents (dispatch, submit, checks, review, accept, send back, message), also with reduced motion. **Not built:** anything in the pantry or the meeting room (Phase 6)

> The MVP bar is met with Phase 5: open a repo, run a real agent in an isolated worktree, have it verified by an independent reviewer with evidence, and watch it happen in the office.

## Phase 6 — Office life

The one part of the office that is **not** a picture of something recorded, so it is fenced in (approved rules): it only ever happens **while an agent is idle or waiting** (never while it is working, or while they have a review to do), everything it shows is labelled **simulated**, it is **on by default with one switch** to turn it off, it is off with reduced motion, it lives only in the picture (nothing is recorded, nothing is ever sent to an agent), and it shows no invented sentences. Built in slices, each checked before the next.

- [x] **6a: Tea, coffee and snacks.** An employee whose agent has been idle (or waiting) for about a minute may, after a random wait of up to two and a half minutes more, walk to the **tea counter** or the **snack shelf**, stand there for 20 to 35 seconds with a cup or a snack in hand, and walk back carrying it. The pace is **calm**: at most a third of the team is away at once (one person may always go), nobody goes again for two and a half minutes, breaks are spread over a few minutes rather than coming in waves, and in the worst case (everyone idle all day) about one in seven is away at any moment. The moment their agent starts working again, or they are given a review, they head back. Their bubble reads the state's own label, **simulated** and _at the tea corner_ (or _at the snack corner_); a demo agent's says **demo** as well. A switch in the office toolbar, **Office life**, is on by default and remembered on this computer only (a browser store; if it cannot be used the office life stays on); with the system's reduced-motion setting it reads off and cannot be switched on, because nobody walks. Verified by unit tests of every rule on a fake clock with a scripted die, a whole simulated day of six people (the cap, everyone getting a turn, breaks spread out, the cooldown), the director's count of free spots, the bubble's three kinds of trip and the setting, each rule checked by mutation (which found three gaps in the tests, fixed), and by watching demo agents take breaks in the running app and turning the switch off. **Not built:** chats at the pantry table, meetings, real messages shown with their real subject (6b)
- [x] **6b: Real messages, shown with their real subject.** When one employee really messages another (or you), a small note appears over the employees involved for six seconds: _to Kei: Quick question_ over the sender, _from Ada: Quick question_ over the recipient (over the employee alone when the other side is you). The subject is the conversation's own, as recorded, made to fit on one line and cut at 48 characters, and if it is not known the note leaves it out (_to Kei_) and never makes one up. Nobody walks anywhere: a message must not pull someone away from real work. It is a picture of a recorded message, so it carries no `simulated` mark (the envelope that flies is the handoff of 5c). The newest note over an employee is the one they show, and a note is text, so it still shows with reduced motion. Verified by unit tests of the mapping from events to notes (who, what it says, unknown subjects and employees, control characters, emoji cut cleanly) and the board of notes on a fake clock, and by watching a chatty demo team exchange real messages in the running app. **Not built:** chats and meetings (6c)
- [x] **6c: Chats and meetings.** Idle employees sometimes go together instead of alone: two or three **chat at the pantry table**, and in a team of six or more three to five **meet in the meeting room**. Each outing is a small group that sets off together, and the chat or meeting begins only once **all** of them are there (the stay is 25 to 45 seconds for a chat and 40 to 70 for a meeting, and it ends for everyone at once). While it lasts, whoever's turn it is (they take turns, a few seconds each) has an **empty "…" bubble marked simulated** over their status bubble, and never any words: there is nothing in it that could be mistaken for a real message. Once a chat or meeting has begun, its members' status bubbles stop repeating where they are, so five of them do not bury the room; the label and the **simulated** mark stay. A real message's subject (6b) always comes before a simulated bubble. The pace is still calm: a chat or meeting takes at most half the team (two may always chat), only when the others it asks along are also idle and free, and more than a third of a small team is away only when it is the one outing on the floor. If one of two goes back to work the other heads back too, and one of three leaving lets the rest go on. What someone fancies falls back to something simpler when it cannot be had (a meeting to a chat, a chat to tea, tea to a chat when both counters are full). Verified by unit tests of every rule on a fake clock with a scripted die (who is asked along, room at the table, the limits, arriving together, dropping out, the turns), a simulated day of a team of twelve with every kind of outing, and mutation checks (which found several gaps, fixed, and some redundant checks, removed), and by watching twelve demo agents chat, meet and have tea in the running app. **Phase 6 is complete.**

## Phase 7 — Customisation

Built in slices, each checked before the next (approved design): a character editor (7a), a role editor (7b), departments (7c) and an office editor (7d). What is customised is always chosen from what Shokuba can draw and check, and stored as data, so a saved choice can never be something that cannot be shown. Agents still only ever receive text you wrote.

- [x] **7a: The character editor.** Every employee has an **appearance** next to their shirt colour: a **skin tone** (six), a **hair colour** (eight), a **hair style** (short, long, bun or bald) and **what they wear** (nothing, glasses, headphones or a cap). Each is one of a fixed set named by an id, validated on the way in, so it is never a free colour or free text. The **form** shows a live preview, drawn from the very geometry the office draws, so what you see there is what you get. Everyone hired before this looks exactly as they did (the default is the old look). The look shows everywhere a person is drawn: at their desk, walking, and sitting at a reading desk. One migration adds the column, an unreadable stored value shows the default instead of breaking anything, and the change is recorded in the event log as an `employee.updated` for the `appearance` field. It can be changed while an agent runs, since it is not a launch setting. Verified by unit tests of the choices and their validation, the service (defaults, refusing bad and partial looks, editing as a whole, surviving a restart and an unreadable value), the migration on an employee hired before it, the geometry of every style and accessory (inside the space a person takes, painted in the right order, distinct from each other), and the preview and its fitting, each checked by mutation, and by looking at six differently dressed employees in the running app and the editor
- [ ] 7b: The role editor
- [ ] 7c: Departments
- [ ] 7d: The office editor (themes, names and decor)
